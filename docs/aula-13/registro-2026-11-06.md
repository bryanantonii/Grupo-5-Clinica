Registro de 6 de novembro de 2026 para documentação e apresentação do Grupo 5.

Integrei os cinco cadastros da gestão e os Relatórios à API NestJS e ao MongoDB. A equipe agora faz login real no Angular, e o perfil determina quais operações pode executar. O mock deixou de ser a fonte de dados da gestão na configuração padrão. O cadastro público, o login e Meus dados do paciente também foram conectados ao MongoDB.

O PR 9 da aula 12 foi integrado à develop com autorização do responsável pelo projeto. Executei o git pull e continuei em clinica/aula13-integracao, preservando a configuração local do Angular. Os arquivos do professor e os testes obrigatórios originais foram mantidos.

## O que cada perfil pode fazer

| Operação | Atendente | Administrador |
| --- | --- | --- |
| Listar, cadastrar e editar os cinco módulos | Permitido | Permitido |
| Confirmar, realizar, registrar falta ou cancelar consulta | Transições válidas | Transições válidas |
| Excluir logicamente os cadastros | Bloqueado com 403 | Permitido |
| Consultar Relatórios | Bloqueado com 403 | Permitido |
| Criar conta de atendente pela API | Bloqueado com 403 | Permitido |

Cancelar uma consulta é uma mudança de status e mantém seu histórico. Essa ação é diferente de excluir um cadastro. A rota DELETE de Consultas também exige administrador; o cancelamento normal da agenda usa PATCH de status.

O paciente tem uma conta separada da equipe: pode criar seu acesso e atualizar os próprios dados, mas não acessa os cadastros nem os Relatórios da gestão.

## Como as camadas se conectam

O login confere e-mail e senha no backend e devolve um JWT de uma hora. O Angular guarda a sessão em sessionStorage, vinculado à aba. O interceptor envia o token somente às rotas privadas da API configurada. O token não é enviado a outros sites nem ao catálogo público.

Na API, JwtAuthGuard verifica primeiro a identidade: token ausente, inválido ou expirado resulta em 401. Depois, PerfisGuard confere a permissão indicada por Perfis: um perfil insuficiente recebe 403. Os botões e menus acompanham essas permissões, mas a barreira final está no backend.

## Persistência dos módulos

| Módulo | Rota da API | Dados e regras principais |
| --- | --- | --- |
| Pacientes | /api/v1/pacientes | E-mail único, nascimento válido, referência a convênio e exclusão lógica. |
| Profissionais | /api/v1/profissionais | Registro e e-mail únicos; referência a Especialidade como ObjectId. |
| Consultas | /api/v1/consultas | Paciente e profissional ativos, expediente, horário único e transições de status. |
| Especialidades | /api/v1/especialidades | Nome único, duração inteira de 15 a 120 minutos e valor não negativo. |
| Convênios | /api/v1/convenios | Nome e ANS únicos, cobertura de 0 a 100 e modalidade preservada. |
| Relatórios | /api/v1/relatorios | Resumo e agrupamentos calculados nas coleções reais; acesso de administrador. |

Os cadastros usam GET, POST, PATCH e DELETE com inativação. Consultas acrescenta PATCH /consultas/:id/status. Os formulários recebem referências da API e enviam os IDs reais do MongoDB, incluindo o convênio do paciente e os participantes da consulta.

## Regras que continuam valendo fora da tela

O servidor recusa dados malformados e campos inesperados. A agenda usa o fuso America/Sao_Paulo, aceita dias úteis futuros entre 8h e antes das 18h e exige uma data com fuso explícito. Um índice único impede duas marcações simultâneas do mesmo profissional no mesmo horário. Cancelar libera o horário.

O fluxo permite marcada para confirmada ou cancelada; confirmada para realizada, falta ou cancelada. Estados finais não podem ser reabertos, e consultas encerradas não podem ser editadas. Atualizações concorrentes de status são conferidas antes de gravar.

## Correção encontrada e seed

A referência de Especialidade em Profissionais estava sendo criada como Mixed, um tipo genérico. Isso permitia gravar o ID como texto e deixava o cruzamento do relatório sem resultado. Corrigi o schema para ObjectId e fiz o relatório aceitar também referências antigas em texto, sem precisar reescrever esses cadastros.

O seed manteve os cinco convênios, três profissionais e o administrador existente. Criou um atendente com senha em hash e completou somente os campos ausentes de duração e valor nas três especialidades. Foram usados os valores fictícios já presentes no C1. Produtos permaneceu ausente.

## Como iniciar neste computador

Na pasta backend, mantenha a conexão do MongoDB no arquivo .env local e execute:

```powershell
npm ci
npm run configurar:auth
npm run seed
npm run start:dev
```

Em outro terminal, na pasta frontend:

```powershell
npm ci
npm start
```

Abra http://localhost:4200/gestao. Sem sessão, a navegação leva a /login. O Swagger está em http://localhost:3000/api/docs.

As contas de teste ficam no .env do backend: SEED_ADMIN_EMAIL e SEED_ADMIN_SENHA para administrador; SEED_ATENDENTE_EMAIL e SEED_ATENDENTE_SENHA para atendente. Consulte os valores no VS Code e digite-os somente no login local. Senhas, URI do MongoDB e segredo JWT não acompanham a documentação nem o Git.

## Respostas de verificação da aula 13

O interceptor prepara cada requisição privada da API com Authorization Bearer e o JWT da sessão. Em 401, limpa a sessão e redireciona para o login. Um erro 403 conserva a sessão, pois a identidade é válida e o problema é a permissão. Respostas antigas não encerram um login mais recente.

Esconder um botão melhora a experiência, mas não impede alguém de chamar a API diretamente. O PerfisGuard consulta o perfil do token e a permissão da rota. Nos testes, atendentes receberam 403 ao tentar DELETE e Relatórios, mesmo sem usar a interface.

Os componentes já dependiam dos contratos dos serviços. Para trocar a fonte de dados, criei os adaptadores HTTP, alterei os providers e defini usarMock como false. Ajustei também as referências reais, as datas, o login, os menus e a visibilidade de ações. A lógica dos formulários continuou compartilhada.

As evidências estão em docs/aula-13/evidencias. O contrato detalhado, o checklist e as respostas das aulas 11 a 13 acompanham o material em Markdown.

## Limites e próximos passos

Esta entrega integra a gestão e as contas dos pacientes. O cadastro público usa /criar-conta, o login do paciente usa /entrar e Meus dados salva na própria conta. O login da equipe usa /login. Os agendamentos públicos permanecem demonstrativos. A recuperação automática de senha ainda não está disponível.

O JWT expira em uma hora. Logout limpa a sessão do navegador, mas não revoga individualmente um token já emitido. Refresh token, revogação e a integração completa do portal do paciente são evoluções posteriores. Use somente dados fictícios neste ambiente acadêmico.

## Cadastro público e conta do paciente

O cadastro público anterior guardava somente um perfil de demonstração no navegador. Por isso, criar conta no site não inseria um usuário no MongoDB. Substituí esse comportamento por cadastro e autenticação reais, preservando o visual do Penpot.

POST /auth/cadastro-paciente grava nome, e-mail normalizado e hash da senha em clinora.usuarios. O servidor fixa o perfil paciente e inicia a sessão. POST /auth/login-paciente valida essa conta. GET e PATCH /conta usam o ID do token para ler e editar apenas os dados do titular. A sessão da equipe e a sessão do paciente têm chaves distintas no navegador.

O paciente não recebe acesso à gestão. O guard recusa esse perfil em rotas administrativas e em rotas privadas sem permissão explícita para paciente. O cadastro e a edição rejeitam tentativas de enviar perfil, status, ID de outra pessoa ou hash. A senha usa bcrypt, com limite de 72 bytes; nenhuma senha vai para o sessionStorage.

## Como demonstrar o cadastro funcionando

1. Abra /criar-conta e preencha dados fictícios, uma senha de teste e a confirmação.
2. Salve. A confirmação só aparece depois que a API grava a conta.
3. No Compass, abra clinora e usuarios. Filtre pelo e-mail informado.
4. Mostre nome, perfil paciente, ativo, createdAt e updatedAt. Não exponha o hash nem os dados de acesso.
5. Entre em Meus dados, altere nome ou telefone e salve. Recarregue a página.
6. Saia e tente uma senha incorreta: o acesso deve ser recusado. Entre com a senha correta: os dados editados voltam do banco.
7. Tente cadastrar o mesmo e-mail: a tela deve informar que a conta já existe.

Na conferência pela interface, usei paciente.portal.20261106@example.com. O nome passou de Cadastro Portal Teste para Paciente Portal Atualizado, e o telefone ficou (51) 99999-2026. A leitura direta no MongoDB confirmou a conta com perfil paciente, senha em hash e os dados editados. As evidências estão em conta-paciente.json e conta-navegador.json.

A conta de acesso é diferente da ficha clínica de pacientes. Não vinculei prontuários antigos pelo e-mail, pois essa identidade ainda não é verificada. Os agendamentos do portal continuam demonstrativos e a recuperação automática de senha não foi implementada nesta correção.
