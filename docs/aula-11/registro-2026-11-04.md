## Escopo desta entrega

ConveniosService foi registrado e exportado pelo ConveniosModule. Ele oferece criar, atualizar, buscar por ID, listar e remover com inativação. Os tipos de entrada delimitam os campos utilizados pelo service; os campos omitidos em uma edição parcial são preservados.

A base anterior do módulo E tinha schema e seed, sem controller HTTP. Esta atividade acrescenta a camada de serviço e seus testes. Não acrescenta rotas, DTOs HTTP, integração do Angular ou autenticação. Assim, o comando de verificação chama o service pelo container do Nest em vez de usar Swagger ou Postman.

O enum modalidade e os valores padrão da atividade anterior foram preservados. A revisão dessa extensão pelo grupo e pelo PO continua pendente. Os fluxos de estados do módulo C e os relatórios do módulo F são responsabilidades dos respectivos módulos. JWT, senhas e perfis pertencem às aulas 12 e 13.

## Parte 1 Regra de código ANS único

RN10 estabelece que dois convênios não podem ter o mesmo código ANS. A regra também vale para um convênio inativo, pois o cadastro continua no banco e mantém sua identificação.

### Modelagem da regra

Pré-condição: foi solicitado um cadastro ou a alteração do código ANS de um convênio existente.

Ação: o service remove espaços das extremidades e consulta se outro documento já usa o código. Na edição, exclui o próprio ID dessa busca.

Pós-condição: quando o código está livre, o cadastro ou a alteração é gravado. O código continua sendo texto, preservando zeros à esquerda, como 045678.

Fluxo alternativo: se outro convênio usa o ANS, o service lança ConflictException com status 409. A gravação solicitada não é feita. O erro identifica o campo codigoAns e apresenta uma mensagem de conflito.

### Casos de borda e concorrência

- Manter o próprio ANS em uma edição é permitido.
- Trocar pelo ANS de outro cadastro é recusado.
- O código de um convênio inativo não fica disponível para um cadastro novo.
- Uma alteração apenas de cobertura não precisa modificar ou reenviar o ANS.
- Duas solicitações simultâneas podem consultar o código antes da primeira gravação. O índice único no MongoDB impede a duplicidade e o service traduz o erro E11000 para conflito 409.

O nome também possui índice único no schema anterior. Sua consulta usa a mesma collation em português com strength 1, considerando equivalentes diferenças de maiúsculas e acentos. A regra é conferida antes da gravação e a colisão do índice também é tratada.

## Onde a regra fica

O método garantirUnicidade concentra a verificação contextual. Criar e atualizar reutilizam essa verificação. TratarDuplicidade converte a colisão do índice em uma exceção de negócio. Outros erros do banco continuam sendo propagados, para não transformar indisponibilidade em uma mensagem incorreta de duplicidade.

O schema confere tipos, limites e formatos, enquanto o service consulta o estado atual do banco. O índice único complementa essa verificação quando há operações concorrentes. Cada camada tem uma responsabilidade que pode ser demonstrada nos testes.

## Parte 2 Inativação e preservação do histórico

RN11 determina que a exclusão de um convênio apenas o inativa e que a listagem padrão mostra os ativos.

Pré-condição: o convênio existe e foi solicitada sua remoção.

Ação: remover altera apenas ativo para false, com validação habilitada na atualização. O service não chama operações de exclusão física.

Pós-condição: o documento permanece com o mesmo ID, os demais campos e a data original de criação. A listagem padrão deixa de mostrá-lo. A consulta por ID e a listagem com todos=true permitem encontrá-lo novamente.

Fluxos alternativos: ID malformado resulta em BadRequestException com status 400; ID válido sem cadastro resulta em NotFoundException com status 404. Repetir a inativação de um cadastro existente continua preservando o documento.

O estado do módulo E é o booleano ativo. Não foi criado um fluxo de status de Consultas dentro de Convênios. A edição pode alterar ativo explicitamente, conforme o tipo de atualização; a remoção sempre define false.

## Testes e conferência real

Foram aprovados 24 testes novos do service. Eles cobrem RN10 e RN11, atualização parcial, zero inicial, nome único, erros do banco, concorrência simulada, busca literal e respostas para ID inválido ou inexistente. Somados aos 17 testes do schema e aos 8 de Produtos já existentes, o backend passou em 49 testes.

Neste Windows, os testes locais usam o resolvedor JavaScript já preparado para evitar o módulo nativo bloqueado pelo Controle de Aplicativo. A configuração versionada de Jest foi preservada. Não foi alterada nenhuma proteção do Windows.

O comando verificar:regras:convenios cria um banco temporário com nome aleatório, registra o model e o service pelo Nest e executa nove grupos de verificações reais. Ele confirmou a preservação do documento inativo, a reserva do ANS e uma única gravação entre duas criações concorrentes. Ao terminar, remove apenas o banco temporário que acabou de criar, após conferir seu nome. Os dados de clinora não são utilizados como dados de teste.

Na pasta backend, com a conexão autorizada configurada no .env local:

```text
npm ci
npm test -- --runInBand
npm run build
npm run verificar:regras:convenios
```

O último comando exige permissão para criar e remover o banco temporário no servidor configurado. Os resultados desta execução estão em evidencias/testes.json e evidencias/verificacao-real.json. URI, senha e tokens não foram incluídos nos arquivos da entrega.

## Respostas para a documentação da aula 11

### Uma regra como pré condição ação e pós condição

RN11. O convênio precisa existir. Ao solicitar a exclusão, o service define ativo=false. O documento continua no banco, mas deixa de aparecer na listagem padrão. Se o ID for inválido, recebe erro 400; se o cadastro não existir, recebe 404.

### O que acontece ao chamar a regra sem usar a tela

O service aplica a mesma verificação para qualquer chamador. Por exemplo, um ANS já utilizado gera conflito 409 e não cria outro registro. Os testes chamam o service diretamente e comprovam isso. Esta branch ainda não expõe controller HTTP de Convênios; a integração dessas chamadas às rotas pertence à etapa correspondente do módulo.
