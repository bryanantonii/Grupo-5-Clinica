# Autenticação da Clinora na aula 12

Registro de 5 de novembro de 2026 para documentação e apresentação do Grupo 5.

Implementei a autenticação da API com usuários no MongoDB, senhas protegidas por
bcrypt e tokens JWT de uma hora. A API agora exige uma identidade válida nas
rotas de gestão. O login e o catálogo público da clínica possuem exceções
explícitas para continuar acessíveis sem token.

## O que foi entregue

| Parte | Resultado |
| --- | --- |
| Usuários | Schema com e-mail único, perfil, situação e timestamps. A senha é gravada somente como hash. |
| Login | POST /api/v1/auth/login compara a senha com bcrypt e devolve accessToken e dados públicos do usuário. |
| JWT | Assinatura HS256, prazo de uma hora e payload com sub, nome e perfil. |
| Guard global | Protege as rotas por padrão; token ausente, inválido ou expirado recebe 401. |
| Rotas públicas | Decorator Publico libera o login e o catálogo de apresentação do site. |
| Seed | Cria o primeiro administrador sem apagar cadastros ou redefinir a senha de um usuário existente. |

## Por que existe um catálogo público

A Clinora já apresenta a equipe sem exigir login do visitante. Criei duas rotas
de leitura em `/api/v1/catalogo`, com nome, registro e especialidade dos
profissionais ativos. Elas não devolvem e-mail, telefone privado ou dados de
acesso. As operações de gestão continuam protegidas pelo guard.

## Como a autenticação funciona

1. O cliente envia e-mail e senha para o login público.
2. O service consulta o usuário e seleciona o hash somente nessa busca.
3. O bcrypt compara a senha digitada com o hash. A senha não é descriptografada.
4. Se os dados estiverem corretos e o usuário estiver ativo, a API assina o JWT.
5. O cliente envia o token no cabeçalho Authorization com o tipo Bearer.
6. O guard verifica assinatura, prazo e formato da identidade antes de liberar a rota.

O token contém `sub`, que é o ID do usuário, `nome` e `perfil`. A biblioteca
acrescenta `iat`, momento de emissão, e `exp`, momento de expiração. E-mail, senha
e hash não entram no payload. A assinatura protege a integridade, mas o conteúdo
do token pode ser lido; ele não deve ser tratado como um documento secreto.

## Senhas e configuração

O bcrypt usa custo 10 e gera um salt aleatório para cada senha. Senhas iguais
podem produzir hashes diferentes. O schema usa `select: false` em `senhaHash`,
e os services escolhem explicitamente os campos públicos das respostas.

O cadastro exige pelo menos oito caracteres e no máximo 72 bytes em UTF-8.
Esse limite evita o truncamento do bcrypt, inclusive em senhas com caracteres
acentuados. O login também recusa entradas acima do limite.

O comando `npm run configurar:auth` prepara as variáveis no `.env` local.
Ele gera o segredo JWT e a senha inicial aleatória sem mostrá-los no terminal.
O segredo precisa ter pelo menos 32 caracteres e não pode ser o texto de exemplo.
O `.env` é ignorado pelo Git e não acompanha a documentação.

## Administrador e novos usuários

O administrador inicial é criado pelo seed a partir de `SEED_ADMIN_EMAIL` e
`SEED_ADMIN_SENHA`. Repetir o seed preserva o ID, o hash, os timestamps e as
edições dos registros existentes.

POST `/api/v1/usuarios` exige um token e cria somente atendentes. O cliente não
consegue enviar `senhaHash`, `ativo` ou escolher `admin`. As permissões por perfil
ainda não foram implantadas: essa é a próxima etapa da aula 13.

## Como testar no Swagger

Na pasta backend, com a conexão do MongoDB configurada no `.env`, execute:

```text
npm ci
npm run configurar:auth
npm run seed
npm run start:dev
```

1. Abra `http://localhost:3000/api/docs` e tente GET `/api/v1/profissionais` sem token. O resultado esperado é 401.
2. Abra o `.env` local no VS Code e consulte `SEED_ADMIN_EMAIL` e `SEED_ADMIN_SENHA`. Use os valores somente no login da aplicação.
3. Em POST `/api/v1/auth/login`, envie os campos `email` e `senha`. O resultado esperado é 200.
4. Na resposta, copie somente `dados.accessToken`, sem as aspas.
5. Clique em Authorize no Swagger, cole o token no campo Bearer e confirme.
6. Execute GET `/api/v1/auth/me` e GET `/api/v1/profissionais`. Ambos devem responder 200.
7. Remova a autorização e repita a consulta protegida para conferir novamente o 401.

O retorno de sucesso continua usando o padrão do projeto: o conteúdo fica em
`dados`. O login não devolve um token diretamente na raiz da resposta.

| Rota | Acesso |
| --- | --- |
| POST /api/v1/auth/login | Público; e-mail e senha válidos emitem o JWT. |
| GET /api/v1/auth/me | Protegido; confere a identidade do token. |
| POST /api/v1/usuarios | Protegido; cadastra um atendente. |
| GET /api/v1/usuarios/me | Protegido; consulta o próprio cadastro sem hash. |
| /api/v1/profissionais e suas subrotas | Protegidas; operações existentes preservadas. |
| GET /api/v1/catalogo/profissionais e /catalogo/especialidades | Públicos; somente apresentação da clínica. |

Nesta etapa, a gestão Angular ainda não envia JWT. Portanto, as telas que chamam
rotas protegidas recebem 401 até a integração da aula 13. A validação desta aula
é feita no backend e no Swagger. O site público continua usando o catálogo real.

## Testes e conferência do banco

Passaram 109 testes no backend e 53 no frontend, além de ESLint, TypeScript e dos
dois builds. Os oito testes obrigatórios de Usuários e Auth passaram sem alteração.

`npm run verificar:auth` executou 31 verificações com a aplicação Nest e MongoDB
real em um banco temporário separado. Foram conferidos o hash, a omissão do hash
nas respostas, a preservação do seed, o JWT de uma hora, as respostas 401 e 409,
os DTOs, os usuários inativos e a continuidade do catálogo público. O banco de
teste foi removido ao finalizar.

No banco `clinora`, o seed criou um administrador. A comparação dos documentos
antes e depois confirmou que os cinco Convênios, três Profissionais e três
Especialidades permaneceram intactos. Produtos continuou ausente. O usuário
foi encontrado com perfil admin, ativo e senha em hash; a consulta comum omitiu
esse hash.

## Respostas para a aula

Autenticação verifica quem está acessando. Na Clinora, isso é feito pelo login e
pelo guard JWT; uma falha resulta em 401. Autorização verifica quais ações essa
identidade pode executar. Os perfis já existem nos dados, mas o bloqueio por
permissão com resposta 403 será implementado na aula 13.

A senha é guardada como hash porque o sistema só precisa conferir se a senha
digitada corresponde à cadastrada. Guardar uma forma reversível permitiria
recuperar as senhas se a chave fosse obtida. O bcrypt faz a comparação e usa um
salt diferente em cada cadastro.

O JWT leva apenas ID, nome, perfil e os tempos de emissão e expiração. Ele não
leva senha, hash ou e-mail, porque seu conteúdo pode ser decodificado por quem
tiver o token. A API usa a assinatura para conferir se ele foi adulterado.
